# Supabase setup for SuyoLink

## Run the SQL

1. Open `supabase/migrations/202609260001_initial_schema.sql`.
2. Copy the entire file into **Supabase Dashboard → SQL Editor → New query**.
3. Run it once using the SQL Editor's default administrative role.
4. Check Table Editor for the nine tables below and Storage for the private `suyo-proofs` bucket.

This is an initial migration for a fresh application schema. It creates tables without dropping existing data. If one of these tables/buckets/functions already exists, the transaction fails and rolls back: inspect the existing schema and make a follow-up migration instead of deleting it. Do not run only selected sections.

The script uses Supabase's existing `auth.users`, `storage.buckets`, and `storage.objects`; do not manually create those schemas in your project.

## Tables

- `profiles`: UUID matching the Auth user, public display name, timestamps. No passwords, email, editable verification flag, or editable points balance.
- `profile_contacts`: the user's private phone and default address. Only that user can read/edit these.
- `suyo_requests`: requester, chosen provider, title, details, category, offer in centavos, PHP currency, deadline, location, notes, status, timestamps.
- `applications`: one application per provider/request, message, pending/accepted/rejected/withdrawn status.
- `proofs`: private Storage object path, provider note, submitted/accepted/rejected status and requester rejection reason. Images live in Storage, not SQL rows.
- `ratings`: one 1–5 rating by the requester for a completed request's provider.
- `notifications`: private in-app notifications generated by workflow events; recipients can mark their own as read.
- `request_events`: append-only task status history with actor and time. This is task history, not a bank/payment transaction ledger.
- `points_ledger`: one 10-point reward per confirmed completion.

Views: `provider_ratings` calculates rating count/average; `my_points` returns the signed-in user's points total, including zero before the first reward. Both respect RLS.

## Auth first

`AuthContext` now uses Supabase Auth for signup, password login, session restoration and logout. Profile names and contacts are read and saved in the database. Email is read-only in the profile editor. `SuyoContext` still stores requests locally; moving requests to the RPCs below is the next integration step.

Configure `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `.env`, then restart Expo. The auth forms call:

```js
await supabase.auth.signUp({
  email,
  password,
  options: { data: { full_name: name } },
});
await supabase.auth.signInWithPassword({ email, password });
await supabase.auth.signOut();
```

`AuthContext` uses `onAuthStateChange` to restore and follow the Supabase session. A database trigger creates profile/contact rows after signup, including backfilling existing Auth users when this migration runs. Profile data is loaded by `session.user.id`, not email.

When email confirmation is enabled, signup displays a check-email message and keeps protected routes closed. Confirm in the browser, then return to the app and log in. Configure a reachable confirmation redirect in Supabase; automatic mobile deep-link sign-in is not implemented. Email confirmation verifies email ownership; it is not government-ID verification. ID review/admin verification is a separate future feature. Do not let users update an `is_verified` field themselves.

The Expo app must only use a publishable/anon key, never a service-role/secret key. Passwords stay in Supabase Auth.

`npm run test:e2e` builds with a fake Supabase project and intercepts HTTP responses in Playwright. It checks login rejection, signup with/without confirmation, session persistence, profile edits, logout, route guards, themes and local requests without creating real accounts or sending email. On Windows with Edge installed, set `$env:PLAYWRIGHT_CHANNEL = 'msedge'` first. Rebuild normally before serving or deploying `dist`; the test build is for tests only. Live email delivery, project configuration and device behavior still require a real-account smoke test.

## Request API

Create requests through the RPC (not a direct table insert):

```js
const { data, error } = await supabase.rpc('create_suyo_request', {
  p_title: draft.title,
  p_details: draft.details,
  p_category: draft.category,
  p_offer_centavos: Math.round(Number(draft.offerAmount) * 100),
  p_deadline: deadlineDate.toISOString(),
  p_location: draft.location,
  p_notes: draft.notes,
});
if (error) throw error;
```

Read the open board:

```js
const { data, error } = await supabase
  .from('suyo_requests')
  .select('*, requester:profiles!requester_id(full_name)')
  .eq('status', 'open')
  .gt('deadline', new Date().toISOString())
  .order('created_at', { ascending: false });
```

Use `requester_id` / `provider_id` to filter the user's own tasks. The frontend should fetch participant tasks separately from the open board. Open request content (including entered location/notes) is visible to all signed-in users; keep private account contact details in `profile_contacts`.

Change the app's camelCase field mapping to the database's snake_case:
`offerCentavos → offer_centavos`, `createdAt → created_at`, `requesterEmail → requester_id` (UUID), `providerEmail → provider_id` (UUID).
The database generates IDs. Do not upload the old `suyo-...` local IDs as UUIDs or automatically migrate requests owned only by a mock email.

## Workflow RPCs

All functions derive the acting user from the session. Never supply requester/provider IDs to impersonate another user.

- `apply_to_suyo({ p_request_id, p_message })`: another user applies to an unexpired Open request. Self/duplicate applications are rejected.
- `decide_application({ p_application_id, p_accept })`: only the requester approves/rejects. Approval assigns exactly one provider and rejects other pending applicants.
- `withdraw_application({ p_application_id })`: applicant withdraws a pending application. Reapplication is not supported in this first version.
- `change_suyo_status({ p_request_id, p_status: 'in_progress' })`: assigned provider starts work.
- `change_suyo_status({ p_request_id, p_status: 'cancelled' })`: requester cancels an Open request. No cancellation after assignment yet.
- `submit_suyo_proof({ p_request_id, p_storage_path, p_note })`: assigned provider submits an uploaded proof, moving the request to Awaiting confirmation.
- `review_suyo_proof({ p_proof_id, p_accept, p_reason })`: requester confirms completion or rejects proof with an explanation. Rejection returns the request to In progress.
- `rate_suyo_provider({ p_request_id, p_score, p_comment })`: requester rates the actual provider after completion.

Status values: `open → assigned → in_progress → awaiting_confirmation → completed`, with `open → cancelled` and rejected proof returning to `in_progress`.

The request row is locked during each workflow change. Direct client writes to workflow tables are intentionally denied, so users cannot skip approvals, edit awards, or forge notifications.

## Proof upload

Use a unique object path: `<request-uuid>/<signed-in-provider-uuid>/<unique-filename>.jpg`.
Upload to `suyo-proofs` with `upsert: false` while the task is In progress, then call `submit_suyo_proof` with that exact path.

The bucket allows JPEG, PNG, and WebP up to 10 MiB. Both the provider and requester can read the images using authenticated downloads or short-lived signed URLs; other users cannot. The app must convert unsupported image formats before upload.

Images cannot be updated/deleted by clients after upload. Rejected proofs use a new image path. Unsubmitted orphan uploads require a future trusted cleanup job using the Storage API, not direct SQL deletion from storage tables. Existing permissive Storage policies on your project must not grant broader access to this bucket.

## Profiles and notifications

```js
await supabase.from('profiles').update({ full_name: name }).eq('id', user.id);
await supabase.from('profile_contacts').update({ phone, address }).eq('user_id', user.id);
await supabase.from('notifications').update({ read_at: new Date().toISOString() }).eq('id', notificationId);
const { data: points } = await supabase.from('my_points').select('*').single();
```

Email changes use `supabase.auth.updateUser({ email })`, not a profile-table update.

## Remaining integration and scope

- Build the application/proof/review/rating screens and connect contexts to these APIs.
- Notifications are database records only; refresh/query them in the UI. Device push delivery and Realtime subscriptions are not configured.
- Points are achievement points, not money. The initial rule is 10 points once per confirmed completion; change the rule in a migration before launch if desired.
- No payment processor, wallet, escrow, payout, dispute system, GPS tracking, or automatic completion.
- Deadline expiry prevents new applications and approval but does not automatically cancel/complete an existing task.
- Account deletion is not exposed in the app. Requests/history retain foreign-key references, so a future trusted account-deletion/anonymization workflow is required.
- Backend anti-abuse/rate limits and the final cancellation/dispute policy still need product decisions.

## Validation

The migration was run against local in-memory PostgreSQL (PGlite) with test Auth/Storage schemas. Tests cover triggers, read policies, unauthorized mutations, the apply/approve/proof/review flow, cancellation, ratings, and duplicate rewards. This does not test Supabase email delivery, actual Storage uploads, JWT issuance, or your live project's existing policies.

Run the repeatable local check (installs the test dependency outside the app):

```powershell
$dbCheckPath = Join-Path $env:TEMP 'suyolink-db-check'
npm install --prefix $dbCheckPath @electric-sql/pglite --no-audit --no-fund
$env:PGLITE_MODULE = Join-Path $dbCheckPath 'node_modules/@electric-sql/pglite'
node tests/supabase-schema.test.cjs
```

After applying the migration, smoke-test real signup and the flow with two Supabase Auth accounts.
